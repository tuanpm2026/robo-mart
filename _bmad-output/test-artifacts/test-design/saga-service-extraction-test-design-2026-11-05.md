# Saga Service extraction test design

Date: 2026-11-05

Verify the [Saga extraction plan](../../planning-artifacts/saga-service-extraction-plan-2026-11-05.md) against durable state, participant receipts and observable business effects. Scenario IDs describe obligations, not a requirement to create one test method per row. Parameterize related cases and use the lowest test layer that proves the invariant; reserve full-stack tests for cross-service behavior.

## Test layers and release gates

| Layer                    | Purpose                                                                                             | Fixtures                                                                                         |
| ------------------------ | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Unit                     | State decisions, cancellation priority, error classification, budget accounting                     | Pure policy inputs, deterministic clock; assert prohibited business actions cannot be scheduled. |
| Contract                 | RPC/Avro compatibility, error/result vocabulary, public response semantics                          | Actual generated proto/Avro sources; signed fixture tokens where relevant.                       |
| Integration              | Transaction boundaries, receipts, SQL claims, concurrency and provider crash windows                | Real PostgreSQL/Kafka/Schema Registry/Testcontainers and real gRPC boundaries where needed.      |
| Full stack               | Independently running services, actual outbox/consumer propagation, authoritative ledgers and stock | Label-verified isolated Compose project; mock provider remains durable.                          |
| Browser                  | Actual Customer/Admin UI, OIDC, pending states, retries, reload and cart acknowledgement            | Playwright Chromium against the isolated stack.                                                  |
| Migration and deployment | Mixed engine ownership, retained data, schema rollout and release provenance                        | Seeded legacy/external records, real manifest rendering and temporary Git remotes.               |

P0 protects money, stock, ownership, accepted-order durability or access boundaries. Every P0 applicable to a phase must pass before that behavior is enabled. P1 covers operational/read-model behavior and must pass before the affected rollout or embedded-engine retirement. Continue enforcing the inherited 80 percent line-coverage gate; coverage is not a substitute for failure-path tests.

## Order participant and concurrency

| ID  | Priority and layer     | Scenario and required assertion                                                                                                                                                                                                                          |
| --- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| O01 | P0 integration         | Inject failure between order insert and START outbox write: both roll back. Commit with publisher/Kafka unavailable: the accepted order and exactly one durable START remain.                                                                            |
| O02 | P0 integration         | Concurrent POST retries with the same user/key create one order, owner binding, snapshot and START request. Replaying the same key with a different semantic request returns a conflict; old rows remain replayable under documented compatibility.      |
| O03 | P0 integration and RPC | Concurrent identical ConfirmCheckout commands produce one transition/history/outbox effect and a reusable command receipt. A changed payload using that commandId is rejected.                                                                           |
| O04 | P0 integration         | Concurrent ConfirmCheckout and BeginCancellation have one valid serial outcome. If cancellation wins, confirmation is rejected and no confirmation event is created. If confirmation wins first, the normal charged-order cancellation path is admitted. |
| O05 | P0 integration         | Race shipping against cancellation admission: if SHIPPED wins, cancellation is rejected and no refund starts; if cancellation wins, shipping cannot commit. Prove the database guard, not only the controller check.                                     |
| O06 | P0 integration and RPC | Reject wrong owner, sagaId, epoch, state or business version. Replaying a recorded successful command after shipping returns its original result; it must not trigger an erroneous refund.                                                               |
| O07 | P0 integration         | BeginCancellation commits state, request sequence and CANCEL outbox atomically. Repeated client/internal cancellation neither duplicates logical requests nor resets budgets. FinalizeCancellation replay creates one cancellation effect.               |

Extend the current Order integration/contract suites and add a focused Order participant RPC integration suite. Preserve [OrderCheckoutSafetyIT](../../../backend/order-service/src/test/java/com/robomart/order/integration/OrderCheckoutSafetyIT.java), [OrderCancellationIT](../../../backend/order-service/src/test/java/com/robomart/order/integration/OrderCancellationIT.java), [PendingPaymentRecoveryIT](../../../backend/order-service/src/test/java/com/robomart/order/integration/PendingPaymentRecoveryIT.java) and [OrderServicePactProviderIT](../../../backend/order-service/src/test/java/com/robomart/order/contract/OrderServicePactProviderIT.java) during the compatibility period.

## Payment outcome closure and refunds

| ID  | Priority and layer     | Scenario and required assertion                                                                                                                                                                                                                                           |
| --- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P01 | P0 integration         | Concurrent charge retries, expired/deleted response cache and process restart leave one provider charge/payment. Preserve existing order/key/user/amount/currency binding and small-pool cases in PaymentIdempotencyIT.                                                   |
| P02 | P0 integration and RPC | GetChargeOutcome returns durable success, final decline, processing or uncertainty correctly. A local FAILED row after a transient error and an absent row before a delayed dispatch are not proof of no charge.                                                          |
| P03 | P0 integration         | Close an order before any charge: persist terminal admission/provider closure; late ProcessPayment, including a different key for the same order, creates zero charges.                                                                                                   |
| P04 | P0 integration         | Pause a caller after application intent acquisition but before provider dispatch. Close the charge, then resume the old caller: it cannot settle. This must be proven at the provider boundary, not just by a new Saga lease.                                             |
| P05 | P0 integration         | Pause after provider settlement but before application finalization. Close/reconcile must report the original successful charge and repair/read its result; it cannot return NO_CHARGE_FINAL.                                                                             |
| P06 | P0 integration and RPC | Race close with a genuinely in-flight provider operation. Return a serialized final outcome or UNKNOWN within the deadline, never a false terminal no-charge result. Do not occupy the application pool while waiting on provider I/O.                                    |
| P07 | P0 integration         | Refund succeeds but response/finalizer is lost; lookup/replay with the same refund key records one refund and correct cumulative refunded amount after restart.                                                                                                           |
| P08 | P0 integration         | Refund decline, outage, timeout and stale finalizer retain recoverable accounting. Concurrent partial/full cancellation refunds cannot exceed the charge; allocate and persist the remaining refund amount atomically and reuse it on retry.                              |
| P09 | P0 integration         | Closure records/receipts remain authoritative after response-cache cleanup and through compatible migration/rollback. Previously refunded or closed orders cannot acquire a fresh charge. Preserve USD/current currency validation and old full-refund identity behavior. |

Extend [PaymentIdempotencyIT](../../../backend/payment-service/src/test/java/com/robomart/payment/integration/PaymentIdempotencyIT.java), [PaymentGrpcIT](../../../backend/payment-service/src/test/java/com/robomart/payment/integration/PaymentGrpcIT.java) and [PaymentMigrationIT](../../../backend/payment-service/src/test/java/com/robomart/payment/integration/PaymentMigrationIT.java). Add focused closure/reconciliation tests using the real independent provider datasource and barriers. Application transaction rollback alone is not a provider-crash test.

## Durable Saga runtime

| ID  | Priority and layer       | Scenario and required assertion                                                                                                                                                                                                                                    |
| --- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| W01 | P0 integration           | Crash/rollback before inbox+workflow commit causes redelivery with no orphan workflow. Crash after commit but before Kafka ACK leaves one workflow and one logical scheduled action.                                                                               |
| W02 | P0 integration and Kafka | Duplicate eventId/business request, rebalancing and replay schedule one operation. Conflicting payload bindings are quarantined without mutating the existing workflow.                                                                                            |
| W03 | P0 integration           | Two workers claim the same due Saga; only the current owner can persist the result/next action. Expired lease takeover succeeds and the stale token cannot commit progress.                                                                                        |
| W04 | P0 integration           | Small connection pool plus a blocked participant: no Saga DB connection/transaction is held for the RPC. Lease/fence logic remains safe after a pause longer than the lease.                                                                                       |
| W05 | P0 integration and RPC   | Persist operation intent, commit participant effect, drop response/kill worker, then restart. Reconcile/replay the same operation key and record the original result without another effect. Parameterize reserve, charge, refund, release and Order finalization. |
| W06 | P0 unit and integration  | Transient transport errors, business rejection and breaker denial follow different branches. Combined workflow/transport retry bounds, next-due times and max-age budgets survive restart; timeout does not imply rollback.                                        |
| W07 | P0 integration           | CANCEL arrives before START, a duplicate START arrives after cancellation, or sequences arrive out of order: persist cancellation intent and reject stale forward work. Validate immutable context even for a cancellation stub.                                   |
| W08 | P1 integration and Kafka | Malformed Avro/raw bytes, unknown request type/version and poison records enter the existing acknowledged DLT path with stable identity; they cannot trigger money/stock operations or silently lose accepted work.                                                |
| W09 | P0 integration           | Retention cannot delete active/manual-review work or CHECKOUT_CONFIRMED records still eligible for cancellation. Old START replay after inbox cleanup cannot recreate checkout for a paid/terminal order.                                                          |

Use the repository's Spring Boot 4, Jackson 3, Testcontainers 2 and @MockitoBean conventions. A new Saga integration fixture needs PostgreSQL, Kafka/Schema Registry and controlled RPC participants; it does not need every business service to run in every module test.

## Cancellation compensation and manual recovery

| ID  | Priority and layer      | Scenario and required assertion                                                                                                                                                                                 |
| --- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| K01 | P0 integration          | Cancel before START/dispatch: close payment admission, release/close Inventory, then finalize. Late START/charge/reserve cannot create effects.                                                                 |
| K02 | P0 integration          | Cancel during unknown/in-flight reserve: stop further charge admission, establish terminal charge outcome and close Inventory safely before finalization.                                                       |
| K03 | P0 integration          | Cancel during charge: UNKNOWN preserves reservation; later charge success refunds once, while terminal no-charge skips refund.                                                                                  |
| K04 | P0 integration          | Charge succeeds but cancellation wins the Order confirmation race: do not confirm; refund -> release -> finalize in that order.                                                                                 |
| K05 | P0 integration          | Cancel a previously CHECKOUT_CONFIRMED order after a worker restart and elapsed idle time. Wake the same workflow identity and return committed stock once.                                                     |
| K06 | P0 integration          | Refund rejection, timeout or unavailable provider retains pending cancellation and held stock. Resolve a lost successful refund using its original key; repeated user cancellation never grants a fresh budget. |
| K07 | P0 integration          | Release fails after refund is confirmed: retry release only; preserve the refund receipt and never issue a newly keyed refund.                                                                                  |
| K08 | P0 integration          | FinalizeCancellation ACK is lost after release; retry its command only. Repeated finalization does not duplicate history/outbox or return stock again.                                                          |
| R01 | P0 unit and integration | Each phase reaches persisted max-age/attempt limits and manual review with unknown money protected. Restart, rebalance or breaker recovery does not reset limits.                                               |
| R02 | P0 integration and HTTP | Authorized resume grants an explicit fresh budget but preserves operation identities and irreversible results. Concurrent resume is idempotent and audited.                                                     |
| R03 | P1 integration          | Operator queries page/filter workflow errors and receipts correctly without reading other service databases or exposing card/shipping payloads.                                                                 |
| R04 | P0 integration          | Manual actions cannot force CANCELLED while refund/release is unknown, bypass shipping guards, or create another charge/refund under a fresh key.                                                               |

## Evidence required for completion

For every fault scenario record the source revision, fixture project, workflow/order IDs, injected boundary, before/after states and actual effect counts. Successful checkout must have one provider charge, one payment, one reservation and one confirmation history/outbox effect. Charged cancellation must have a full confirmed refund and one stock restoration. Charge-free cancellation must have zero provider charges. For a Saga that is still uncertain, require nonterminal business state and held stock.

Use mock provider ledger rows as financial evidence in addition to application payment rows. Inventory proof needs quantities, reservation state and movements, plus eventual Product stock version/projection where applicable. Repeated delivery can involve multiple send attempts; assert one logical business event identity/effect rather than incorrectly requiring exactly one network publication.

Keep retry/lease/closure tests deterministic with barriers, database time and bounded polling. Do not use long sleeps to manufacture an assumed race. Restore stopped containers, fault flags and test-owned data in finally/AfterEach. Never remove volumes or stop unverified containers.

Run the [implementation plan's verification commands](../../planning-artifacts/saga-service-extraction-plan-2026-11-05.md#verification-commands-during-implementation) at the relevant phase. Record future results under `_bmad-output/test-artifacts/`; the scenario matrix itself does not mark any new Saga behavior as passing.
