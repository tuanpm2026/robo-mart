## What Went Well

### 1. WebSocket/STOMP Real-Time Push Worked First Try

Story 7.1 introduced Spring WebSocket + STOMP + SockJS on Notification Service plus the API Gateway `/ws/**` proxy and a SockJS+STOMP.js frontend client. The architecture decision to authenticate JWT only on STOMP CONNECT (not per message) kept the `JwtStompInterceptor` simple. AdminPushService wraps every push in try/catch so WebSocket failures cannot break Kafka consumers — a clean separation of concerns. Only 3 review patches needed (toast on reconnecting transition, Resume scroll behavior, payload validation on inbound — added in Story 7.4).

### 2. CQRS Reporting Done Pragmatically Without New Infrastructure

Story 7.3's "CQRS read model" is implemented as live queries against the existing Order Service database — no separate read store, no event projection, no async sync delay. `ReportService` exposes `rebuildReadModels()` as a no-op-with-timestamp because queries are always live. This pragmatic decision avoided a multi-week investment in a separate read database while still satisfying the FR. Charts (bar/doughnut/line) rendered via PrimeVue's bundled Chart component — no Chart.js install needed.

### 3. DLQ Admin UI Closes the Operational Loop

`failed_events` table + V3 Flyway migration + `DlqConsumer` persistence + paginated DataTable with expandable rows + retry endpoints. Operators can now see failed events, expand to inspect payload preview + error class, and retry single events or trigger retry-all. The simplification — retry marks event RESOLVED (full Kafka replay deferred) — is acknowledged in story Tasks and review (deferred items 5/6). Duplication guard added during review (`existsByOriginalTopicAndAggregateIdAndStatus`) prevents flood of duplicate DLQ rows.

### 4. System Health Aggregation Across 7 Services

Story 7.4's `HealthAggregatorService` pings `/actuator/health` and 4–6 metric endpoints per service in parallel via `parallelStream()`, with 3-second timeouts to fail fast. Total sweep stays under 5s even with services down. The `ServiceConfig` record cleanly encodes per-service capabilities (`hasDb`, `hasKafka`, `consumerGroup`) so Cart Service and API Gateway correctly skip HikariCP/Kafka metrics. WebSocket push every 10s via `HealthPushScheduler` keeps the UI fresh without polling. Caching `latestHealth` (added during review) prevents the REST endpoint from triggering a fresh sweep on every load.

### 5. PrimeVue 4.x Tabs API Adopted Cleanly

Story 7.2 was the first use of PrimeVue 4's new Tabs API (`Tabs` / `TabList` / `Tab` / `TabPanels` / `TabPanel`) — separate imports each, no deprecated `TabView`. Pattern documented in Dev Notes for future reuse. Count-up animation built without a third-party library using `requestAnimationFrame` + easeOut cubic — avoids new dependency.

## What Could Be Better

### 1. Story 7.3 Review Caught 12 Patches — Highest of the Epic

The CQRS reporting + DLQ story had the most issues at review time:
- `retryAll()` loaded all PENDING events with no upper bound — OOM risk
- `Instant.parse()` on user-supplied query params with no try/catch → 500 on malformed date
- `SUM()` returning null for empty date ranges → NPE casting to BigDecimal
- Native `DATE()` query: `row[0].toString()` NPE if `created_at` is null
- `useToast()` called inside async Pinia action body (outside Vue setup context)
- No upper bound on `size` query param for DLQ list
- `findRevenueByProduct` GROUP BY missing `productId` (productName collisions possible)
- Conflicting sort: method name `findByStatusNotOrderByFirstFailedAtDesc` + `PageRequest` Sort both applied
- `DlqAdminRestController` queried repository directly, bypassing service layer
- DlqConsumer had no idempotency guard (added: `existsByOriginalTopicAndAggregateIdAndStatus`)

These are all input-validation / null-safety / unbounded-input issues — same pattern category as Epic 5's "concurrent action guard" gap. The action item was checklist-driven for UI but did not extend to backend input validation.

### 2. Story 7.4 Review Caught 12 Patches — Same Volume in System Health

- `ActuatorMetricResponse.firstValue()` returned `measurements.get(0)` without filtering by `statistic == "VALUE"` (could return COUNT or MAX instead of the requested quantile)
- `actuatorStatus === 'DOWN'` check missed UNKNOWN/OUT_OF_SERVICE statuses (changed to `!== 'UP'`)
- `lastUpdatedLabel` computed once and froze — needed 1s ticker
- `lastUpdatedLabel` showed negative seconds when client clock behind server
- `KafkaLagIndicator` didn't guard negative `currentLag`
- DB Pool row rendered as `5/null` when `dbPoolMax` null
- `getOrderEvents` returned 200 with empty array for non-existent orderId (changed to 404)
- WebSocket payload not validated before passing to store
- `updateLagHistory` called for all 7 services including non-Kafka ones
- `p95Seconds` NaN/Infinity not guarded before cast to Long
- `fetchMetric()` swallowed all exceptions silently — no log even at debug
- Test `memoryPercent_computedCorrectly` did not actually invoke the service

Pattern: defensive-coding gaps on the boundaries (HTTP responses, WebSocket payloads, Actuator metric semantics). Similar shape to Story 7.3.

### 3. Defense-in-Depth Gap Compounded by 4 More Admin Controllers

Epic 7 added 4 admin controllers (`ReportAdminRestController`, `PaymentAdminRestController`, `DlqAdminRestController`, `AdminSystemHealthRestController`) — none with `@PreAuthorize`. Total project now has ~7 admin controllers across 4 services, all relying on gateway-only RBAC. Direct service access bypasses ADMIN role check. Risk grew silently this epic.

### 4. WebSocket Token Expiry Mid-Session Not Handled

Explicitly deferred in Story 7.1 (review item). STOMP authenticates once on CONNECT; if JWT expires during a long admin session, the connection stays alive against an expired token. Reconnect would reuse the stale token. This is fine for short sessions but a long-lived admin dashboard could surface auth-state confusion.

### 5. Solo Dev Pace Variability Across Stories

Story 7.1 (3 patches) and Story 7.2 (6 patches) shipped relatively cleanly. Stories 7.3 and 7.4 each landed ~12 patches in review. Both later stories had broader scope (multi-service backend changes + chart-heavy frontend / metrics aggregation across 7 services). Pattern: scope-heavy stories with new domain (CQRS, Actuator, charts) need slower, more deliberate first-pass implementation.

## Key Insights

### Recurring Patterns

1. **Boundary-validation gaps (4/4 stories):** Every story had at least one review patch on input parsing, response shape, null safety in DTOs, or external system response handling (Actuator). Particularly evident at: HTTP query params, native SQL result rows, Actuator JSON, WebSocket inbound payloads.

2. **Solo-dev review still finds CVE-shape issues:** No path traversal this epic (no file I/O), but unbounded `retryAll()` (DoS shape), unhandled `DateTimeParseException` (500 instead of 400), and missing 404 for non-existent orderId all surfaced via review. The 3-layer review process continues to justify itself.

3. **Pragmatic-over-pure architecture decisions paid off:** Live CQRS queries instead of separate read store; AdminPushService swallowing all exceptions; retry-marks-RESOLVED instead of full Kafka replay. Each decision documented and deferred items captured. Velocity preserved, technical debt visible.

### Technical Patterns Established

1. **WebSocket+STOMP convention:** JWT validated only on CONNECT via `ChannelInterceptor`; AdminPushService is fail-safe (try/catch wrapping every push); records as payloads (Jackson 3.x serializes automatically); SockJS factory URL is `http://` not `ws://`.

2. **Health aggregation convention:** `ServiceConfig` record encoding `hasDb`/`hasKafka`/`consumerGroup`; `parallelStream()` with exception-safe per-service handler returning DOWN sentinel on any failure; 3-second connect+read timeouts; `latestHealth` cache field plus 10s scheduler push.

3. **Reports/charts convention:** PrimeVue Chart component (no separate Chart.js install); `Object[]` row → typed-record mapping with explicit casts and null guards; `JOIN i.order o` for OrderItem aggregations; native query for date-bucketing.

4. **DLQ admin convention:** `failed_events` table with `(originalTopic, aggregateId, status)` idempotency check; service-layer mediation between controller and repository; status as VARCHAR with CHECK constraint (deferred enum refactor).

### Process Insights

- **Epic 7 was the most "platform" epic so far:** new transports (WebSocket), new operational tools (DLQ admin, health monitoring), new query patterns (CQRS read). Patches per story were higher than admin-CRUD epics (Epic 5) because each story explored unfamiliar territory.
- **First use of new UI patterns slows velocity:** PrimeVue 4 Tabs (7.2), PrimeVue Chart (7.3), Transition for expand/collapse (7.4) — first instances took longer; second instances will be faster.
- **Multi-service stories amplify review surface:** Story 7.3 touched order, payment, notification, and gateway services — natural patch count growth.
