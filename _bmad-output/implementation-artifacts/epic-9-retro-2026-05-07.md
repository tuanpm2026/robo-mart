- Sprint-status reports during that window misrepresented Epic 9 progress
- A retro held mid-window would have shown 1/3 done, 1/3 in-progress, 1/3 done — confusing
- For a solo project this is harmless; on a team, it would have blocked dependent planning conversations

## What Went Well

### 1. Distributed Tracing Bridged Three Protocols Cleanly

Story 9.1 established trace propagation across REST (auto-instrumented via OTel + Spring MVC observation), gRPC (`ObservationGrpcClientInterceptor`/`ObservationGrpcServerInterceptor` registered as global interceptors via Spring gRPC 1.0 auto-config), Kafka (`observation-enabled: true` + custom `CorrelationIdKafka{Producer,Consumer}Interceptor` for the business correlation ID layer), and WebSocket (manual `x-trace-id` STOMP native header injection). The TraceId-vs-CorrelationId separation (W3C `traceparent` for OTel, `X-Correlation-Id` MDC for business logs) was architecturally clean and showed up well in the patch list — F1, F13, F14 were tight refinements rather than re-designs.

### 2. K8s Manifests + ConfigMap Override Pattern Validated

Story 9.2's choice to **not** use Spring Cloud Config Server and instead lean on Spring Boot relaxed binding (`SPRING_DATASOURCE_URL` env → `spring.datasource.url` property) produced a clean override hierarchy: base `application.yml` → profile block → ConfigMap → Secret. Documented explicitly in the story, then leveraged for free in 9.3 to satisfy AC1 (service discovery) — no extra code needed because the ConfigMap already mapped `ORDER_SERVICE_URL`, `GRPC_CLIENT_INVENTORY_SERVICE_ADDRESS`, etc. to K8s DNS names. 24 manifests created in one story without surprises.

### 3. Audit Trail via AOP Avoided Cross-Cutting Code Bloat

Story 9.3's `@Auditable` + `AuditAspect` + `AuditEventListener` design kept audit recording out of business code entirely. Adding audit to a method became a single annotation. The decision to use `@Order(LOWEST_PRECEDENCE)` so audit runs after `@Transactional` commit (best-effort audit on success) was an explicit accepted tradeoff documented in the review — pragmatic for a learning project, with the failure mode (JVM crash between business commit and audit write) acknowledged. The `EntityIdProvider` interface + SpEL `entityIdExpression` fallback pattern handled the variety of return types across order/inventory/payment/product without per-service bespoke logic.

### 4. Reconciliation Architecture Correctly Routed to notification-service

Placing the reconciliation jobs in `notification-service` rather than `order-service` was the right call: notification-service already had `RestClient` instances for all services (via `HealthAggregatorService`), `AdminPushService` for WebSocket alerts, and `@EnableScheduling` configured. Order-service stayed focused on order processing. Variance thresholds were configurable (`inventory-threshold-percent: 1.0`, `inventory-threshold-absolute: 5`) rather than hardcoded — caught in review patch and fixed.

### 5. Review Caught Real Bugs Before Merge

Notable Epic 9 catches:
- 9.1 F4: `probability: 1.0` in production would burn observability budget — replaced with `${TRACING_SAMPLE_RATE:1.0}` env override (ConfigMap then sets it to `0.1` for K8s).
- 9.2 D2: `localhost:9094`/`localhost:9095` hardcoded for gRPC clients — would have caused all Saga gRPC calls to fail in K8s. Replaced with env interpolation.
- 9.3: `BigDecimal amount` truncated to `Long` in `ReconciliationSummaryResponse` — silent precision loss in money values, caught and fixed.
- 9.3: `Instant.parse()` on user input did not handle `DateTimeParseException` — would have produced 500 instead of 400 on malformed timestamps in audit query endpoints. Fixed in all 4 services.
- 9.3: `AuditAggregatorService` URL params not URL-encoded — query injection vector, caught.

## What Could Be Better

### 1. Process Gap on Closing Story 9.2

Story 9.2 sat in `in-progress` for ~3 weeks while technically complete. Reasons (reconstructed): the story shipped as YAML configuration + manifests with no follow-up dev tasks, so there was no natural "next commit" trigger to remind the closer to flip status. The flip itself only happened on 2026-05-07 alongside the eventual retro. Story 9.3 was developed and closed against 9.2's technical state directly, which papered over the gap.

The fix is mechanical: add a status flip to the same commit that lands the dev agent record (or run a sprint-status check at the end of every dev session). Solo project so the cost was low; on a team it would have blocked dependent work.

### 2. Multi-Instance Reconciliation Locking Not Addressed

The Story 9.3 reconciliation scheduler runs `@Scheduled` cron jobs in `notification-service`. In a multi-pod K8s deployment (HPA min 2, max 5 from Story 9.2), all replicas will fire the cron simultaneously and run the same fan-out reconciliation against inventory/payment/order services, multiplying load and potentially producing duplicate alert pushes via WebSocket.

This mirrors the unresolved **Multi-instance deployment racing on dead saga recovery** debt from Epic 8 (`DeadSagaDetectionJob` has the same problem). Both want the same primitive — a distributed lock (Redis SETNX or DB advisory lock) — and neither got one. Carrying this forward.

### 3. Reconciliation Endpoints Use Full Table Scan

W8: `findAll()` on `inventory_items`, `payments`, and active `orders` for reconciliation summary. Acceptable at current scale but will degrade with table growth. Pagination was deliberately deferred but should not be left unbounded indefinitely.

### 4. Audit Trail is Best-Effort, Not Guaranteed

Documented and accepted tradeoff. JVM crash between business commit and audit write loses the audit record. For a real production audit/compliance use case, an outbox-style approach (write `audit_log` row inside the same transaction, then drain to a separate sink) would be needed. Acceptable for a learning project; flagged here so it does not silently become production policy.

### 5. Dev Profiles Strip `prometheus` From Actuator Exposure

W1: Local dev Prometheus scraping does not work without overriding `MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE`. The K8s ConfigMap fixes this in cluster, but local Grafana setup is fiddly. Pre-existing.

### 6. Memory Limits May Be Tight for Heavy Services

W2: `512Mi` limit applies uniformly across all 7 services. Product-service (Elasticsearch + Redis + Postgres + Kafka client + outbox poller) and order-service (Saga state machine + gRPC client + Kafka) are the most likely to exceed this. Needs load data to tune; pre-existing decision.

### 7. HPA Is CPU-Only

W3: JVM workloads can exhaust heap and OOM long before CPU saturates. CPU-only HPA will not scale up in that pattern. Memory-based HPA needs Prometheus Adapter — out of Epic 9 scope.

## Key Insights

### Recurring Themes

1. **Configuration-by-environment-variable is the project's de facto Config Server.** Spring Boot relaxed binding + K8s ConfigMap covers ~95% of the use case at zero infrastructure cost. The decision in 9.2 to skip Spring Cloud Config Server was vindicated by 9.3's free service-discovery satisfaction.
2. **Cross-cutting concerns belong in common-lib via AOP.** `CorrelationIdFilter` (Epic 1+), `GlobalExceptionHandler` (Epic 1+), `AuditAspect` (9.3) — all live in common-lib, all auto-discovered via `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`. Pattern is now well-proven.
3. **Variance-threshold semantics need both percent AND absolute.** Reconciliation uses `>1% OR >5 units` — pure percent breaks for low counts (0→1 is infinite percent), pure absolute breaks at scale. Same insight applies to any future SLO/alerting work.

### Process Insights

- **Skipping retros is locally cheap, globally expensive.** Three skipped retros (6, 7, 8) meant Epic 9 inherited a stale action-item list. For solo work this is workable but the drift is real.
- **Status flip is part of "done", not after.** The 9.2 administrative delay would have been caught by any process that ties status flip to the final commit.
- **Backend-only epics produce different review-patch profiles.** Epic 9 had ~30 patches across 3 stories vs Epic 5's ~70 across 5 stories with frontend. Frontend stories generate more patches per story (UX edge cases, concurrent guards, framework quirks). Backend infra stories generate fewer but more architecturally-load-bearing ones (env-var defaults, transaction ordering, hardcoded addresses).

## Closing

Epic 9 delivered the observability and operations backbone the project had been advancing toward since the structured logging foundations of Epic 1. Distributed tracing now spans REST, gRPC, Kafka, and WebSocket with both OTel `traceId` and business `correlationId` propagated. Every service has K8s health probes, percentile metrics, and a deployment manifest with HPA. Every state-changing operation in the four DB-backed services produces an audit record, queryable by actor, action, entity, time, or trace.

The largest non-technical lesson of the epic was the 3-week administrative gap on closing Story 9.2. No bytes were missing; only the status flip was. For a solo learning project this cost nothing real, but it surfaced the principle clearly: **finishing means flipping the status, not just shipping the diff**. Carrying that forward as the single most actionable process improvement.

Three retros skipped (6, 7, 8) means action items have drifted; this retro reaches back to Epic 5's baseline and acknowledges that. With Epic 10 already complete, the project arrives at a natural reflection point: the original PRD scope is done, and any further work is now in production-hardening territory drawn from the cumulative deferred list.

Net Epic 9 outcome: 3/3 stories shipped, ~30 review patches absorbed, 8 new deferred items, 0 production incidents, observability and operations posture meaningfully closer to production-grade.
