## What Went Well

### 1. Notification Service Bootstrapped From Zero in One Story

Story 6.1 stood up an entire new microservice (module + pom + application config + Flyway migration + JPA entity + Kafka consumer + REST client + mock email service + 15 unit tests + 3 integration tests) in a single day. Pattern reuse from `product-service` (Kafka consumer config) and `order-service` (pom layout, application.yml structure) made this near-mechanical. Notification-service deliberately excludes `security-lib`, `proto`, and `spring-grpc` — kept the dependency surface minimal.

### 2. Architectural Pivot Caught Early — PaymentProcessedEvent Gap

Story 6.1 dev notes flagged that `PaymentProcessedEvent` Avro schema exists but has no publisher (payment-service has no outbox poller, only gRPC). Rather than scope-creep into adding outbox infrastructure to payment-service, Story 6.1 derived payment status from `OrderStatusChangedEvent` transitions:
- `newStatus=CONFIRMED` → payment succeeded
- `newStatus=CANCELLED` + `previousStatus=PAYMENT_PROCESSING` → payment failed

Clean workaround documented in story; payment-service outbox publisher explicitly deferred to a future story.

### 3. Story 6.2 Surfaced and Fixed a Latent Saga Bug

While adding `OutboxPollingService` to inventory-service for `stock_low_alert`, the dev correctly identified that the inventory outbox table also contains `stock_reserved` and `stock_released` events written by `InventoryService.reserveStock()`/`releaseStock()`. **These events were never being published** — the order-service saga consumes them, so the saga was broken (or relying on something else). Story 6.2 added publishing for all three event types, repairing a silent gap from Epic 4. This is exactly the kind of cross-cutting bug that pattern-spread reveals.

### 4. DLQ Implementation Used Spring Kafka's Official Mechanism

Story 6.3 reused `DeadLetterPublishingRecoverer` rather than rolling a custom recoverer. Key decisions documented in dev notes:
- DLQ producer must use `KafkaAvroSerializer` (not `ByteArraySerializer`) because the recoverer receives already-deserialized Avro `SpecificRecord` objects
- DLQ consumer uses `SPECIFIC_AVRO_READER_CONFIG=false` to read any event type as `GenericRecord`
- `@Qualifier` used to disambiguate two `ConsumerFactory<String, Object>` beans
- `setDeliveryAttemptHeader(true)` is on `ContainerProperties` in Spring Kafka 4.0.4, not `DefaultErrorHandler` (corrected during dev — recorded in debug log)

The integration test (`DlqRoutingIT`) uses a `@MockitoBean NotificationService` that throws `RuntimeException` on every method call to force the recoverer path; an inner `@TestConfiguration` listener captures DLQ messages into a `BlockingQueue`. Clean test pattern reusable for any future service that needs DLQ.

### 5. Idempotency Designed Pragmatically Per Notification Type

Story 6.1 review (Decision D1) discovered no dedup guard — fixed via unique constraint `uk_notification_order_type UNIQUE (order_id, notification_type)` plus pre-send `existsBy` check plus `DataIntegrityViolationException` catch. Story 6.2 then made deliberate, type-specific choices:
- `CART_EXPIRY_WARNING` → store `cartId` in `order_id`; unique constraint prevents duplicate warnings per cart
- `LOW_STOCK_ALERT` → leave `order_id` NULL (PostgreSQL treats NULL != NULL); each stock-drop event is a legitimate alert, multiple per product expected

Documented inline in story 6.2 dev notes with revised approach explanation. Each type's idempotency semantics match its business meaning.

## Challenges & Struggles

### 1. Idempotency Gap Found Late in Story 6.1

The biggest review finding (D1) was that the initial implementation had no protection against duplicate notifications on consumer rebalance or retry. Critical bug — would have shipped customers receiving multiple identical "order confirmed" emails. Required a Flyway migration, repository changes, exception handling, and a refactor of `sendOrderConfirmedNotifications()` to fetch the order once instead of twice (which itself fixed another patch — double HTTP call to order-service per CONFIRMED event).

Lesson: Kafka at-least-once + email = idempotency is not optional. Add to checklist for any new event consumer that triggers external side effects.

### 2. Avro CharSequence Trap (Recurring)

Avro-generated string fields return `CharSequence`, not `String`. `event.getOrderId().toString()` is required before any comparison or use. Caught in Story 6.1 dev notes as a callout, but still surfaced as a deferred item ("Null Avro event fields .toString() NPE") — meaning at least one code path hadn't been hardened. Avro schema enforces non-null for required fields so the deferral was accepted, but the pattern keeps biting.

### 3. Docker Daemon Required for Integration Tests — Unavailable in Dev Loop

Both Story 6.1's `NotificationIntegrationIT` and Story 6.3's `DlqRoutingIT` could not be executed during development because Docker Desktop was not running. Tests are structurally correct and compile, but coverage is provisional until CI runs them. This pattern is becoming the norm — tests written, "compile verified, awaiting Docker for execution" appears in two of three stories' completion notes.

### 4. Multi-Instance Hazards Exposed by Schedulers + Pollers

Story 6.2 added two scheduled jobs in two services:
- `OutboxPollingService` in inventory-service (every 1s)
- `CartExpiryWarningScheduler` in cart-service (every 30 min)

Review decision D1 fixed the outbox poller with `SELECT FOR UPDATE SKIP LOCKED`. Decision D2 explicitly accepted the cart scheduler racing risk on the rationale that notification-service deduplication will catch duplicate warnings. This shifts safety to a downstream layer — works, but couples otherwise independent services for correctness. Not pretty, but pragmatic for current single-instance deployment.

### 5. Cross-Service Coupling via Direct REST Calls

Notification-service bypasses the API Gateway and calls `order-service:8083` and `product-service:8081` directly. This works only because admin endpoints have no `@PreAuthorize`. Two coupling concerns:
- Service-to-service calls without service mesh / mTLS
- Local DTOs (`OrderDetailDto`, `ProductInfoDto`) shadow upstream DTOs — must be kept in sync manually

Acceptable today; would not survive proper RBAC hardening (Epic 8) without a notification service-account pattern.

### 6. `@Transactional` Wrapping HTTP Calls

Review patch in 6.1: `NotificationService` methods were `@Transactional` and held a DB connection during the HTTP call to order-service. Fixed by removing `@Transactional` from the orchestration method and only making the repository save transactional. Easy mistake to make when the method "saves to DB at the end" — but the network call is the dominant duration.

## Key Insights & Patterns

### Recurring Bug Patterns

1. **Idempotency design must be per-notification-type** — One unique constraint can serve multiple semantics depending on what's stored in the indexed column (or NULL for "always allow").
2. **Avro `CharSequence` → always `.toString()`** — Carried forward from earlier epics, still surfacing.
3. **`@Transactional` over network calls** — The "save at the end" mental model traps devs into wrapping HTTP calls in transactions. Watch for it in all consumer/orchestrator code.
4. **Hardcoded URLs/credentials in `application.yml`** — 4 of the 13 Story 6.1 patches were "X hardcoded without env-var substitution". Need a config audit checklist for new services.

### Technical Patterns Established

1. **Kafka consumer convention** (notification-service): `KafkaAvroDeserializer` + `SPECIFIC_AVRO_READER=true`, `FixedBackOff(1000L, 3)`, `DeadLetterPublishingRecoverer` wired in (Story 6.3 retrofit), `setDeliveryAttemptHeader(true)` on `ContainerProperties`.
2. **DLQ infrastructure pattern**: separate `dlqProducerFactory` / `dlqConsumerFactory` with `@Qualifier`; DLQ consumer reads `GenericRecord` (schema-agnostic); `extractIntHeader`/`extractLongHeader` for binary-encoded DLT headers.
3. **Notification idempotency pattern**: unique constraint `(order_id, notification_type)`; per-type semantic choice of what to store in `order_id` (cart ID, order ID, or NULL).
4. **Outbox + saga discovery pattern**: When you add an outbox poller for a service, **audit all eventType values being written** — Story 6.2 caught `stock_reserved`/`stock_released` that would have remained unpublished.
5. **Service-to-service REST enrichment pattern**: local DTOs (no cross-service imports), graceful fallback on error (`"Product #" + id`), `defaultStatusHandler` for non-throwing error paths, simple in-memory cache for low-volume/repeated calls (Story 6.2 D3).
6. **Mock implementation gated by `@Profile("!production")`** — `MockEmailService` cannot accidentally ship to prod.

### Process Insights

- **A new service is cheaper than expected when patterns are mature** — Notification-service in 1 day. Module skeleton, Flyway, Kafka consumer, Spring Boot 4 quirks all known.
- **Pollers/schedulers need racing-condition review at design time** — Not "is the lock present?" but "what happens if N instances run this simultaneously?" Story 6.2's two schedulers both needed this discussion.
- **DLQ retrofit was scoped correctly to one service** — Story 6.3 deliberately limited DLQ to notification-service. Inventory/cart use outbox retry; their failure mode is different. Avoided the "DLQ everywhere" trap.

### Team Agreements

- **Idempotency-first for new Kafka consumers**: Every consumer that triggers external side effects (email, payment, gRPC) gets a dedup guard at design time, not via review. Pattern: unique constraint + pre-send `existsBy` + `DataIntegrityViolationException` catch.
- **Don't `@Transactional` an HTTP call**: Orchestration methods that perform network I/O must not hold DB transactions. Move `@Transactional` down to the repository save.
- **Avro `.toString()` ritual**: Treat any Avro string field as `CharSequence` and call `.toString()` immediately on extraction. Add to PR checklist.
- **DLQ scope stays narrow**: Don't propagate DLQ to inventory/cart/order — they have outbox retry. Notification-service is the canonical DLQ consumer.

## Key Takeaways

1. **A new microservice in one day is now normal** — Notification-service stood up cleanly using established patterns (`product-service` Kafka config, `order-service` pom/yaml, test-support Testcontainers). Investment in patterns earlier in the project pays compounding dividends.
2. **Idempotency is the silent killer of event-driven systems** — One review catch (D1 in Story 6.1) prevented duplicate-email spam to customers. Every Kafka consumer with side effects needs dedup designed in, not reviewed in.
3. **Outbox audit reveals saga gaps** — Story 6.2's "let me also publish `stock_reserved`/`stock_released` while I'm here" repaired silent infrastructure that the order saga depends on. Cross-cutting work surfaces cross-cutting bugs.
4. **DLQ done right uses Spring Kafka's official mechanism** — `DeadLetterPublishingRecoverer` + qualified beans + `GenericRecord` consumer. No custom recoverers. Pattern is reusable for any service.
5. **Deferred work growth slowing** — 9 new items vs 15-25 in recent epics. Scope discipline + mature patterns visible.
6. **Defense-in-depth gap is now structurally embedded** — Notification-service depends on admin controllers having no `@PreAuthorize`. Epic 8 will have to address this with a service-account or internal auth pattern, not just a sprinkled `@PreAuthorize`.

## Closing

Epic 6 delivered notifications and event-driven communication on time and on scope, adding a new microservice plus DLQ infrastructure with proportionally fewer deferred items than recent epics. The 3-layer code review continued to earn its keep — Story 6.1's idempotency catch alone justified the process for the entire epic. Pattern reuse from Epics 1-5 turned what could have been a multi-day service bootstrap into a single-day exercise.

Two structural concerns carry forward into Epic 7 and beyond. First, notification-service now structurally relies on the admin-controller `@PreAuthorize` gap that Epic 5's retro flagged — meaning Epic 8's resilience hardening will need to address auth, not just sprinkle annotations. Second, the DLQ infrastructure is logging-only today; Story 7.3 needs to take ownership of replay/management UI and metrics. Epic 7 begins with both Kafka real-time feed (Story 7.1) and dashboard metrics (Story 7.2) fully unblocked; 7.3 needs a design alignment first. Net assessment: clean epic, ready to move forward.
